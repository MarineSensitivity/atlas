# S1 · OPFS persistence pin

Verdict for spike S1 (`atlas-0 scaffold + spikes.md`, Step 4 / Deliverable 6). Raw measurements:
`spikes/1/RESULTS.md` — every number below cites the section it comes from. This file decides; it
does not re-measure, except where it says "re-confirmed".

## The question

Which `@duckdb/duckdb-wasm` version can the app actually **persist** an OPFS database with (write it,
close, reload, read it back with the network cut), and what is the fallback matrix for every way that
can fail — second tab, no OPFS at all, another engine? The plan (D3) makes OPFS a *tier 2*
optimization the app "never requires", so the pin question and the fallback question are one decision.

## Method

`spikes/1/` installs three `@duckdb/duckdb-wasm` builds side by side under npm aliases — `1.32.0`,
`1.33.1-dev57.0` (npm `latest`) and `1.33.1-dev64.0` (npm `next`) — each self-hosting its own mvp+eh
wasm/worker through `?url` imports with a same-origin `new Worker(bundle.mainWorker)`. A page opens
`opfs://atlas-spike.duckdb` READ_WRITE, runs `CREATE TABLE t AS SELECT * FROM '<v9
tables/taxon.parquet>'`, `CHECKPOINT`, closes; Playwright reloads the page **in the same persistent
context** with S3 blocked and re-counts. Separate specs drive the raw second-tab `db.open()` race, the
Web Locks `ifAvailable` flow from D3, and an OPFS-unavailable fault injected inside the worker's own
realm. Chromium 153, WebKit 26.6, Firefox 155; every scenario has a seeded fault so the suite's exit
code means something.

## The numbers the verdict rests on

Every successful `SELECT count(*)` in every run, on every engine and pin, returned **37067** — the
counts never disagree, only the persistence does (RESULTS § "Full matrix — round 0").

| pin | chromium persistence | firefox persistence | webkit |
|---|---|---|---|
| `1.32.0` | **PASS** 37067 → 37067 | **PASS** | fails: OPFS itself is unavailable |
| `1.33.1-dev57.0` (npm `latest`) | **FAIL** — reopen throws `Catalog Error: Table with name t does not exist!` | **FAIL**, same error | fails: OPFS unavailable |
| `1.33.1-dev64.0` (npm `next`) | **PASS** 37067 → 37067 | **PASS** | fails: OPFS unavailable |

- **Re-confirmed 2026-09-21 for this verdict** (`npx playwright test --project=chromium
  e2e/persistence.spec.js e2e/web-locks.spec.js`, exit 0): `1.32.0` ✓, `next` ✓, `latest`/dev57 ✘
  (the `test.fail()`-annotated expected red), all three Web Locks cases ✓. `npm view
  @duckdb/duckdb-wasm dist-tags` still reads `latest = 1.33.1-dev57.0`, `next = 1.33.1-dev64.0` — a
  plain `npm i @duckdb/duckdb-wasm` today still installs the build that silently loses writes.
- **WebKit is a flat failure for all three pins, identically** (RESULTS § "WebKit OPFS: a real,
  pre-existing failure in this environment"): inside a dedicated Worker,
  `navigator.storage.getDirectory()` rejects with `UnknownError: The operation failed for an unknown
  transient reason (e.g. out of memory).` before any file handle is requested. No pin changes this.
- **Web Locks `ifAvailable` is the mechanism that works** (RESULTS § "Web Locks `ifAvailable`"):
  while tab 1 holds `atlas-opfs:<dbName>`, tab 2's request returns `null` and it answers from a
  fresh in-memory database in **1010.9 ms (chromium) / 2371 ms (firefox) / 3292 ms (webkit)**, with
  `createSyncAccessHandle` never appearing in its console — it never touches `opfs://` at all. After a
  graceful release *and* after an abrupt `page.close()`, a fresh tab acquires the lock and reads the
  real persisted file (661.7–1766 ms). The seeded fault — the same probe with a plain
  `navigator.locks.request` and no `ifAvailable` — hangs for the full timeout on **every** engine
  (6001–6024 ms, never resolving early).
- **Raw second-tab race, no lock wrapper** (RESULTS § "Gate 2"): rejects cleanly in 536–1784 ms on
  chromium/firefox, never hangs; the rejection message is engine-specific (`Access Handles cannot be
  created…` vs `No modification allowed:`), so error-string matching is not a portable detector.
- **OPFS-unavailable → in-memory fallback** returns 37067 on all three engines and all three pins.

## What was NOT measured, and why it matters

- **No real private/incognito window on any engine.** "OPFS unavailable" is simulated by rewriting the
  worker script's body before it executes (RESULTS § "Method note"). Real private mode may fail at a
  *different* call — `createSyncAccessHandle` rather than `getDirectory` — so the fallback must wrap
  the whole open-and-write sequence in one `try`, not guard a single call.
- **Playwright's WebKit 26.6 is not Safari.** The measured failure is that engine build in this
  environment, headless and headed alike. It does not license the claim "Safari cannot persist"; it
  licenses only "the app must never require OPFS", which is D3 already. Any user-facing statement
  about Safari needs a real device.
- **Timings are from this machine** (macOS 15.7.1, Node 24.9.0, local dev server, ~1 MB source
  table), not the CI runner and not a phone.
- **The Web Locks flow ran at one DuckDB version** (`pkg=132`). The lock API is browser-side and
  version-independent, but the combination "the lock holder also owns the DuckDB handle's lifetime"
  was exercised only there.
- **Nothing about tier-2 scale.** One ~1 MB table, one release, one db file. No quota pressure, no
  browser eviction mid-session, no LRU of cell tiles, no concurrent writer, no measurement of what a
  10–25 MB per-release store costs to write or re-open. atlas-2 must measure that when it builds it.
- **`1.32.0` vs `next` was not decided on performance** — both pass identically; the choice below is
  about which is a stable, reproducible artifact.

## Consequences — rules later phases inherit

1. **`package.json` carries `@duckdb/duckdb-wasm` at exactly `1.32.0`** — no caret. `^1.32.0` would
   admit a future stable `1.33.x`, and the write bug lives in the `1.33.1` line with no stable
   `1.33` release in existence to test. `next` (`1.33.1-dev64.0`) also passes, but it is a *moving
   dist-tag* pointing at a dev build: not a reproducible pin. Changing this version is a change that
   must re-run `spikes/1/e2e/persistence.spec.js` on chromium **and** firefox, and dev57 must stay red.
2. **Worker/bundle wiring (atlas-2):** self-host the `mvp` + `eh` bundles through `?url` imports and
   construct the worker yourself — `new Worker(bundle.mainWorker)`, same-origin — never duckdb-wasm's
   `createWorker()` helper, and never the `coi` bundle (Pages cannot send COOP/COEP). Keep
   `@duckdb/duckdb-wasm` in `optimizeDeps.exclude`.
3. **Never open OPFS outside a lock.** `navigator.locks.request("atlas-opfs:<dbName>", { ifAvailable:
   true }, cb)`; a `null` callback argument means another tab owns the file → run in memory. A plain
   `locks.request` is a measured hang, not a slow path.
4. **Hold the lock for the whole lifetime of the OPFS handle**, not just for the create. Releasing it
   as soon as the create resolves (or rejects) lets a second tab into the same file — that was a real
   bug in this harness's first round, and it is the same bug an app would write.
5. **Every OPFS path is a `try`/`catch` with an in-memory database as the catch.** Feature-detect by
   attempting the open, not by sniffing `navigator.storage` (which exists in the WebKit worker and
   still rejects). Do not branch on the rejection's message text — it differs per engine.
6. **Explicit `CHECKPOINT` before close; one handle per file.**
7. **OPFS is an optimization, never a precondition.** The memory store is the default path and the
   tested one (D3, Risks). No feature may be unavailable because OPFS is.

Client-side COG display is not S1's question; it is decided in `S3.md` (no).

**Verdict:** OPFS persistence works and is safe to use as a tier-2 cache, but only pinned away from
npm `latest`, only behind Web Locks `ifAvailable`, and only with an in-memory fallback on every
failure path (including all of WebKit as measured here) — pins: `@duckdb/duckdb-wasm@1.32.0`.
