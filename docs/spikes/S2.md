# S2 · First paint without WASM (and the maplibre-gl pin)

Verdict for spike S2 (`atlas-0 scaffold + spikes.md`, Step 4 / Deliverable 6). Raw measurements:
`spikes/2/RESULTS.md`. Two things are settled here: whether tier 0 really paints with zero DuckDB
bytes, and which `maplibre-gl` version and wiring the app is built on — which is a **security**
decision as much as a build one.

## The question

Does the shell + MapLibre + the v7 zones PMTiles + one score COG through titiler, fed only by
`manifest.json` (+ a stubbed `boot.json`), reach a real first paint within **2.5 s with zero DuckDB
bytes requested**? And: does `maplibre-gl` 6.x work under Vite 8, or must the app pin `<6` the way
CalCOFI Explorer did (`atlas-refs/calcofi explore review.md` §11 lesson 10)?

## Method

`spikes/2/` builds the shell against the real v7 manifest (zones PMTiles `programarea_2026-01`,
score COG `…/cog/usa05/d20874edf0c43166.tif`, `rescale 0–90`, `spectral_r`) with 20 real Program-Area
scores and one zone's 8 rescaled components pasted into `public/boot.json`. Playwright blocks
`**/*.wasm` and `**/duckdb*`. The gate metric is **`firstDataFrame`**: the first `render` tick at
which `gl.readPixels` at *both* known ocean points reads back a non-background colour — re-checked
every tick, not `map.once("render")` (which fires on an empty background frame and can never go red).
Nine cold runs, fresh browser process and context each, HTTP cache disabled via CDP; cross-origin
bytes from CDP `Network.loadingFinished.encodedDataLength`.

## The numbers the verdict rests on

**First paint** (RESULTS § "Timing table: FCP, firstDataFrame, zonesPainted, idle — cold profile,
9 runs"):

| mark | median | range |
|---|---|---|
| FCP | 24.0 ms | 16.0–28.0 ms |
| `firstDataFrame` | **499.1 ms** | 467.8–573.9 ms (budget 2500 ms) |
| `zonesPainted` | 456.3 ms | 429.4–507.5 ms |
| `idle` | 1078.2 ms | 1007.6–1098.2 ms |

Zero duckdb/wasm requests before `firstDataFrame` in every run; by `idle` every run converges on 6 S3
requests / ~30 KB (pmtiles header + directory + leaves) and 28 titiler requests / ~62.3 KB. The gate
is falsifiable: a seeded 3 s delay on S3 + titiler pushes `firstDataFrame` to **3507.7 ms** and the
assertion fails (RESULTS § "Gates", seeded fault (c)).

**Critical path size** (RESULTS § "gzip critical-path bytes"): maplibre-gl + pmtiles + CSS alone are
**292.86 KB gzip** (282.15 JS + 10.71 CSS) of the 350 KB budget — 84 % spent before a single line of
app code.

**The advisory** (RESULTS § "npm audit — precise advisory facts", cross-checked against GitHub's own
advisory record, and independently verified by the orchestrator): `GHSA-jrc7-96c5-q579`
(CVE-2026-85061), **critical, CVSS 3.1 score 10.0**, "XSS sanitizer bypass in `DOM.sanitize()`",
`vulnerable_version_range` **`<= 6.4.0`**, `first_patched_version` **`6.4.1`**. All **35** published
5.x releases (5.0.0 … 5.24.0) are inside that range; **no 5.x release is or will be patched**. npm
`latest` is 6.10.0 (re-checked 2026-09-21).

**maplibre-gl 6.10.0 under Vite 8** (RESULTS § "Corrected 4-cell matrix"): starts and paints in all
four cells (`vite dev` / `vite build`+`preview` × with/without `optimizeDeps.exclude`) with named
imports + `setWorkerUrl`. There is no default export in 6.x: a default import is a dev-time
`SyntaxError` and a hard Rolldown build failure, `[MISSING_EXPORT] "default" is not exported by
node_modules/maplibre-gl/dist/maplibre-gl.mjs`.

**Correction found while re-running the 6.10 matrix for this verdict.** RESULTS' build cells report
"the worker asset IS emitted … no 404, no `requestfailed`", on the strength of the pixel gate. The
pixel gate is **raster-only** and cannot see a dead worker. Re-run of the same harness at 6.10.0 with
the RESULTS wiring (`maplibre-gl/dist/maplibre-gl-worker.mjs?url`), built and served by `vite
preview`:

- `dist/assets/maplibre-gl-worker-CupLwWe3.mjs` (19,007 B) is emitted — but it is copied **verbatim**,
  and its own `import … from "./maplibre-gl-shared.mjs"` (513,898 B in the package) is never emitted.
- The page logs `GET /assets/maplibre-gl-shared.mjs → net::ERR_ABORTED` (404). The worker never runs.
- Result: `firstDataFrame = 697.3 ms` (raster paints fine — no worker needed), but
  `isSourceLoaded("zones") = false`, `queryRenderedFeatures({layers:["zones-line"]}) = 0`,
  `marks.zonesPainted` and `marks.idle` never fire, and the spec times out. **No vector tile ever
  parses.**
- Changing one character of wiring — `?worker&url` instead of `?url` — bundles the worker with its
  shared chunk into one file (`maplibre-gl-worker-CNLXcz58.js`, 508,485 B raw / **143,898 B gzip**)
  and the whole gate goes green in 1.7 s. Measured on all four cells with that wiring:
  `vite dev` + exclude `firstDataFrame` 921.6 ms / `zonesPainted` 660.8 ms; `vite dev` without exclude
  802.3 / 615.2; `vite build` + `preview` with exclude — gate passes, 10 rendered zone features;
  without exclude — **byte-identical build output** (same hashes `index-BRnFCl5P.js`,
  `maplibre-gl-worker-CNLXcz58.js`), i.e. `optimizeDeps.exclude` is dev-only and irrelevant to the
  build.

## What was NOT measured, and why it matters

- **The 2.5 s gate was never run on the CI runner.** Every timing here is this machine and this
  network. The 5× headroom is large, but the subplan's gate is worded "on the CI runner" and that
  number does not exist yet. atlas-2's first CI run of a real map page must record it before anyone
  claims the budget is met.
- **Chromium only, headless, swiftshader.** No WebKit or Firefox first-paint numbers, no phone
  viewport, no throttled network, no cold TLS to S3/titiler from a cold DNS cache.
- **titiler was up.** S3's session saw `titiler-v8` unreachable for an extended window. With it down,
  `firstDataFrame` as defined here never fires at all — the degraded path (zones, tables, flower and
  report render; rasters blank) is a *design requirement* from the plan's Risks section that no test
  in this spike exercises. atlas-2 owes it a spec.
- **Only 6.10.0 was exercised, in one page's shape**: one raster source, one PMTiles vector source,
  one `setStyle(diff:true)`. Not exercised: terrain, globe projection, the RTL-text plugin, custom
  layers, `addImage`, popups (which is precisely where the sanitizer advisory lives). A `^6.10.0`
  range admits future 6.x releases nobody has run.
- **No exploit was attempted** for GHSA-jrc7-96c5-q579. The decision rests on the published
  vulnerable range and patch, not on a demonstration; whether the app would ever reach
  `DOM.sanitize()` (popup/attribution HTML) is not the test — shipping a known-critical dependency is.
- **The 19 KB vs 144 KB worker difference was measured only at 6.10.0.** With `?worker&url` the worker
  is a *bundled* artifact whose size follows whatever the package ships.

## The security decision, stated plainly

The subplan's written fallback — "if dev or build breaks, pin `^5.24` and say so" — is **rejected**.
It would knowingly ship a critical (CVSS 10.0) advisory with no patched release in the 5.x line, for
the lifetime of the app, to avoid a build problem that turns out to be one query-parameter wide.
6.10.0 is the patched line *and* it works under Vite 8 — but only with a specific wiring, and the pin
is worth nothing without it. **The pin depends on:** named imports (no default export exists),
`import workerUrl from "maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url"` followed by
`setWorkerUrl(workerUrl)` — `?url` alone produces a build that paints rasters and silently renders no
vector data — and a test that asserts a *vector feature rendered*, not just that pixels are painted.

## Consequences — rules later phases inherit

1. **`maplibre-gl` at `^6.10.0`** (caret, so a future patch for the next advisory lands without a
   plan change; the lockfile still pins the exact build for `npm ci`). Never `<6`: every 5.x is inside
   `GHSA-jrc7-96c5-q579`.
2. **Import it named**, e.g. `import { Map, addProtocol, setWorkerUrl, type StyleSpecification } from
   "maplibre-gl"`. A default import is a hard build failure in 6.x, not a style preference.
3. **Worker wiring (atlas-2/3):** `import maplibreWorkerUrl from
   "maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url"; setWorkerUrl(maplibreWorkerUrl);` — the
   `worker` part is load-bearing. `?url` copies the worker without its 514 KB shared chunk and you get
   a map with no vector layers and no error in the map's own API surface.
4. **Any map spec must assert a rendered vector feature** — `map.isSourceLoaded(id)` **and**
   `map.queryRenderedFeatures({ layers: [...] }).length > 0` — in addition to a pixel probe. Raster
   tiles paint with a dead worker; a `gl.readPixels` gate alone is not a check.
5. **`canvasContextAttributes: { preserveDrawingBuffer: true }`** on the `Map` constructor. The bare
   top-level `preserveDrawingBuffer` of the CalCOFI-era code is silently ignored in 5.x/6.x and every
   out-of-process `readPixels` then reads `(0,0,0,0)` while the map visibly renders.
6. **`map.resize()` immediately after construction.** Without it, raster tile requests were
   non-deterministic under headless Chromium — sometimes never issued at all within 20 s.
7. **Do not add `maplibre-gl` to `optimizeDeps.exclude`.** 6.10 works with and without it in dev, and
   the build output is byte-identical either way; the exclude list stays for
   `@duckdb/duckdb-wasm` only (where it is about self-hosted wasm, not workers).
8. **Compose one style, apply with `setStyle(style, { diff: true })`** — unchanged (D-settled, lesson
   3); this spike's harness is the working example.
9. **First paint may not depend on the worker or on titiler.** Tier 0 (`boot.json` + static HTML)
   renders the table and flower with no map at all; the zones layer and the score raster are
   enhancements.
10. **Budget warning for atlas-2/3:** the critical path is already 292.86 KB gzip of 350 KB with
    maplibre + pmtiles alone, leaving ~57 KB for all app code. Separately, the 143,898 B gzip worker
    is emitted as an *asset*, not a static import, so `scripts/size-budget.mjs` (which walks the
    manifest's `imports`) does not see it — a real 144 KB runtime download that is currently
    unbudgeted. atlas-2 should extend the budget script to count the entry's `assets` too.

Client-side COG display is decided in `S3.md` (no); this spike's relevance is only that titiler is on
the first-paint path and its outage mode is untested.

**Verdict:** tier 0 paints in 499 ms median with zero DuckDB bytes, and `maplibre-gl` 6.x is adopted
over the subplan's `^5.24` fallback because no 5.x release escapes the critical advisory
GHSA-jrc7-96c5-q579 — the pin holds **only** with named imports, `?worker&url` + `setWorkerUrl`, and a
vector-feature assertion in the gate; pins: `maplibre-gl@^6.10.0`.
